# 证据链协同：从任务拆解到可验证交付的多 Agent 实践

多 Agent 的价值不是同时打开多个窗口，而是把复杂任务拆成相互制约的职责链：有人负责理解目标，有人专门找风险，有人收集证据，真正写入由单一执行者完成，最后再由独立验证者复核。

## 一、完整生命周期

`理解 → 并行讨论 → 主控汇总 → 用户确认 → 单写者执行 → 独立验证 → 交付或回滚`

每一阶段都有明确产物。讨论阶段不能直接改生产文件；执行阶段必须保留变更范围；验证阶段要返回可复查的测试输出。没有证据的“应该成功”只能算推断。

## 二、角色分工

| 角色 | 主要问题 | 默认权限 | 输出 |
| --- | --- | --- | --- |
| Planner | 目标、边界、依赖是什么？ | 只读 | 分解方案与验收标准 |
| Contrarian | 哪些假设可能错？ | 只读 | 风险清单与止损点 |
| Researcher | 代码、文档和运行事实是什么？ | 只读 | 来源和证据 |
| Executor | 怎样以最小范围实施？ | 按主控授权 | 变更摘要与回滚点 |
| Verifier | 是否真的达到完成标准？ | 复核优先 | 测试结果与未验证项 |

主控 Agent 负责合并结果、识别分歧、等待用户确认，并保证同一文件只有一个写入者。

## 三、并发基线

并发上限建议从 2 个子 Agent 开始。并发不是越高越好：共享写入范围、依赖未完成或上下文重复时，应改为串行。应根据任务复杂度、成本与可用性调整分工与并发规模。

## 四、确认门禁与证据等级

低风险只读检查可以直接进行；覆盖文件、外部同步、服务配置和公开发布属于方向性操作，必须在动作前再次确认。完成状态分为：文件已修改、测试已通过、已提交或部署、运行中已验证、用户体感已验证，以及仍需长期观察。汇报时逐级说明，不能把“提交成功”写成“用户已验证”。

## 五、失败请求的处理方式

常见失败包括会话绑定失效、请求超时、配置校验失败和后端未降级。处理顺序应是：保留错误原文与时间范围；确认失败发生在哪一层；用最小只读复现区分模型、会话、网络和服务问题；修复后重新执行同一验收用例；最后记录仍未验证的部分。不要因为界面出现通用错误提示，就直接把原因归结为某个项目或某条待办。

## 六、公开仓库的边界

本仓库只发布通用角色模板、工作流和验证规范，不包含工作台实现、生产部署配置、私人知识库、真实运行日志、个人路径、账号、密钥或自动公开发布脚本。工作台仍处于完善阶段，后续应作为独立项目单独评审。

## 七、可复用的最小验收清单

1. 五类角色配置可以解析。
2. 只读角色不会修改目标文件。
3. 执行前存在确认门禁。
4. 同一写入范围只有一个执行者。
5. 验证报告区分已验证、已记录和待观察。
6. 公开材料完成敏感信息扫描。

这套方法的核心不是增加模型数量，而是让分工、权限、证据和责任边界可检查、可复盘、可回滚。
